# 飞控网络连接故障复盘（2026-07-21）

## 结论

本次故障发生在“串口服务器 TCP 角色配置”层，不是网线、IP 可达性或 QGC MAVLink 解析首先失效。

故障时，USR 串口服务器的设备地址是 `192.168.1.200`，工作模式却为 `TCP Client`，目标地址也填写为它自身的 `192.168.1.200:4019`。QGC 的 TCP Link 同样是主动客户端，因此两端没有 TCP Server，`ping` 可以成功，但 `4019` 没有监听者。

现场修复后，串口服务器配置为：

- 设备 IP：`192.168.1.200/24`
- 工作模式：`TCP Server`（协议值 `3`）
- 本地端口：`4019`
- 串口：`57600 / 8N1`
- “TCP Server 踢掉旧连接”：关闭

设备已返回保存和重启成功确认，重启后 `ping` 及 TCP Server 可达性均验证成功，QGC 已由操作员确认可以连接飞控。

## 时间线

1. 网线连接后，PC 可以 ping 通 `192.168.1.200`，USR-M0 也能搜索到设备，但 QGC 无法连接。
2. 现场检查确认 PC 有线网卡为 `192.168.1.5/24`，ARP 中设备 MAC 为 `D4-AD-20-F3-76-C8`。
3. `192.168.1.200:4019` 初始 TCP 握手失败；QGC 进程也没有 `4019` 会话。
4. 通过厂商 UDP 1500 配置协议读取完整参数，确认 `WorkMode=1`（TCP Client）、目标地址为设备自身。
5. 仅将 `WorkMode` 从 `1` 改为 `3`，其余 62 字节串口/网络参数原样回写；设备读取回验通过。
6. 重启设备后，`4019` 开始监听，QGC 可以建立连接。
7. 防复发处理中关闭“踢掉旧连接”，防止调试软件或端口探测建立短连接时挤掉正在工作的 QGC。

## 根因与促成因素

### 直接根因

串口服务器与 QGC 都充当 TCP Client，且串口服务器把远端地址错误配置为自身 IP。网络层没有任何一端监听 `4019`。

### QGC 侧促成因素

工作区原有的 `GRobot_Default` 初始化代码存在三个缺口：

1. 默认写入 `autoConnect=false`，启动后仍需人工连接。
2. 只要存在任意其他持久化连接，就放弃创建 GRobot 默认连接。
3. 只按名称判断，不能识别用户已经创建但名称不同、端点相同的 TCP 配置。

本机实际持久化配置名为 `test`，端点是 `192.168.1.200:4019`，并非 `GRobot_Default`。防复发代码现在会按“默认名称或固定端点”识别它，并确保自动连接，同时不覆盖无关连接。

### 操作侧促成因素

- `ping` 只证明 IP/ICMP 可达，不能证明 TCP 端口、MAVLink 心跳或串口参数正常。
- 串口服务器此前启用了“新连接踢掉旧连接”。普通 TCP 探测也会短暂建立客户端连接，可能挤掉 QGC，因此不能在已连接状态下随意运行端口探测。
- USR-M0“搜索到设备”只证明配置通道可用，不等于飞控正在输出有效 MAVLink。

## 防复发控制

### 已完成

- 串口服务器固定为 `TCP Server / 4019 / 57600 8N1`。
- 关闭“TCP Server 踢掉旧连接”，保留最多 4 个客户端的原配置。
- QGC 默认端点改为启动自动连接。
- QGC 初始化逻辑可以复用名称不同但端点相同的既有 TCP 配置。
- 添加只读诊断脚本 `tools/diagnostics/check-grobot-link.ps1`。

### 现场开机顺序

1. 飞控和串口服务器先上电。
2. 确认有线网卡仍为 `192.168.1.5/24`。
3. 等待串口服务器启动完成，再启动 QGC。
4. 观察 QGC 是否出现载具；不要把“能 ping 通”当作连接完成。

### 无侵入检查

QGC 已连接时运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\diagnostics\check-grobot-link.ps1
```

正常状态应为 `QGC_TCP_ESTABLISHED`。脚本检测到现有 QGC TCP 会话时不会另开探测连接。

只有在 QGC 明确处于断开状态时，才使用端口探测：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\diagnostics\check-grobot-link.ps1 -ProbePort
```

此时 `TCP_SERVER_REACHABLE_QGC_DISCONNECTED` 表示设备端口正常，问题位于 QGC 连接或 MAVLink 数据层；`TCP_SERVER_UNREACHABLE` 才表示应先检查串口服务器工作模式和端口。

## 分层排查顺序

1. `DEVICE_UNREACHABLE`：检查供电、网线、PC 有线网卡 IP、设备 IP。
2. `TCP_SERVER_UNREACHABLE`：检查设备是否为 TCP Server、本地端口是否为 4019、配置是否保存并重启。
3. TCP 已建立但 QGC 无载具：检查飞控串口是否为 MAVLink、波特率是否为 57600、TX/RX 接线与 MAVLink HEARTBEAT。
4. 连接建立后又断开：检查是否有其他调试软件占用连接、设备供电或网线抖动；记录 QGC TCP 日志后再判断是否需要自动重连策略。

## 更换飞控主板后的现场复验（2026-07-21）

更换另一块飞控主板并重新上电后，本次未修改串口服务器、QGC 或新飞控的任何参数，也未发送解锁、起飞等控制指令。复验步骤和证据如下：

1. 保持串口服务器为 `TCP Server / 192.168.1.200:4019 / 57600 8N1`，给新飞控和串口服务器上电。
2. 运行无侵入诊断脚本（不带 `-ProbePort`），结果为 `QGC_TCP_ESTABLISHED`。
3. 核对系统 TCP 会话：`192.168.1.5:3523 -> 192.168.1.200:4019` 为 `ESTABLISHED`，所属 QGC 进程 PID 为 `13776`。
4. 核对 QGC 载具界面：QGC 已识别 ArduPilot，显示飞行模式、电量遥测及 `PreArm: Waiting for RC` / `Not Ready` 状态。
5. 到此停止连接测试，不进行解锁、起飞或参数写入。

复验结论：新主板下的 TCP 传输、MAVLink 心跳和 QGC 载具解析均正常。`PreArm: Waiting for RC` / `Not Ready` 是飞控的解锁前检查状态，不是网络连接失败。上述本地源端口和 PID 每次启动可能变化，只用于本次证据留档，不应写入固定配置。

## 回滚

如果现场设备必须恢复原工作方式，可在 USR-M0 中把工作模式改回 `TCP Client`；原始目标是 `192.168.1.200:4019`。该原配置无法与当前 QGC TCP Client 架构配合，仅用于故障回退记录，不应作为正常运行配置。
