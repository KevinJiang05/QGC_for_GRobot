## 现场症状：切换操控模式时画面偶发卡顿

**已确认的机制。** 视频帧要回到 GUI 线程才能交付显示：
`gstqgcqvideosink.cc:153` 在 `QVideoSink` 所属线程调用 `setVideoFrame()`。
GUI 线程长时间被占住时，新帧交付不了。这一点官方 v5.1.5 也一样。
（复核：渲染线程仍可能显示已交付的帧，"停多久就精确冻多久"是近似说法。）

**定制代码里与飞行模式有关的只有一处**：状态面板的一行文字
（`FlyViewCustomLayer.qml:64`、`DeepSharkStatusPanel.qml:234`）。它不改变视频区域几何，不触发重连。

**模式播报在 GUI 线程同步执行，这一点已由复核确认。**
`Vehicle.cc:1824` 在模式变化时播报，`AudioOutput.cc:254` 在同一线程直接调用语音引擎的入队；
引擎对象在 `QGCApplication.cc:297-304` 初始化，没有迁到工作线程。复核查了 Qt 6.11 的两个 Windows 语音后端：

- SAPI 后端：开始播报是异步提交，不等整段播完；但"立即停止"是同步清队列。
- WinRT 后端：每次播报先同步停止上一段，流就绪后还要在引擎所在线程（也就是 GUI 线程）创建并启动音频输出。
- 队列计数达到 20 条时 `AudioOutput.cc:255` 会执行一次立即停止。
- 中文界面下播报文本是 `手动manual飞行模式` 这类中英混合文本，而引擎在有 `en_US` 语音时固定用英文音色。这是发音问题，不能单独证明卡顿。

**它是不是卡顿的原因，仍未证实。** 复核还指出了我没查的其他 GUI 路径：

- 工具栏的飞行模式下拉面板每次打开和关闭都同步创建、卸载内容（`FlightModeIndicator.qml:63`、`MainWindow.qml:597-604`）。只在点工具栏时适用。
- `MAVLinkEventManager.cc:25-31`、`GuidedActionsController.qml:157`、`FollowMe.cc:172` 都订阅了模式变化。
- 工具栏模式文字宽度变化引起的重新布局。

另有一条历史线索：复核提到 2026-09-28 的旧版本记录里，有"静音后切换增益时卡顿消失"的记载。本轮没有复测，不能当作当前版本的结论。

**实验方法**（按复核建议细化）：固定三路视频、布局和窗口大小，分三组做——用手柄切模式、只开关工具栏下拉不改模式、用工具栏改模式；
每组各做一遍开声音和静音。静音后改善只说明与语音路径有关，具体是哪个调用还要用性能采样定位。

### 条件性 S0（推进器 PWM 直测）

这个功能在飞控**上锁**状态下把某一路输出改成 Disabled，再用 `DO_SET_SERVO` 直接给 PWM。
这条路径绕过了 ArduSub 的解锁和失控保护，停转完全依赖 QGC 随后发出的回中指令。
已有的保护：只允许上锁时开始、时长上限 5 秒、默认 1550、开始前回读原功能并先落盘恢复记录、解锁即中止、回中确认后才恢复功能参数。
界面也写明了"通信中断时可能无法回中，请准备独立的断电停止手段"（`ThrusterMappingTool.qml:1711`）。

**固件侧的依据（复核补充）。** ArduPilot 源码里，`DO_SET_SERVO` 对 Disabled 输出直接写 PWM，不启动任何计时
（`AP_ServoRelayEvents.cpp:27-61`）；只有 repeat 路径才带延时和回 trim。输出通道的直接 PWM 标记会让该值持续写出。
也就是说"输出会一直保持"有源码依据。尚未做的是：与实际部署的固件版本逐行对上，以及台架实测。

**T01 回中指令只发一次；心跳中断后不再尝试回中，链路恢复也不会自动恢复。**
- `DO_SET_SERVO` 不在 QGC 指令队列的重试名单里，只发一次（`MavCommandQueue.cc:200-228`、`:331`）；回执超时阈值 1200 毫秒、每 500 毫秒检查一次。
  回中的回执没收到，就进入"需要人工恢复"（`ThrusterDirectControlController.cc:504-510`），不再发第二次。
- 心跳中断时，`_vehicleUnavailable()`（`:586-598`，由 `:66-70` 触发）直接转入"需要人工恢复"并停掉全部定时器，包括测试时长定时器。
- 链路恢复后没有自动动作，必须由人点"恢复异常通道"。

后果成立的条件：测试 PWM 已经到达飞控，而回中指令没有到达。回执丢失本身不等于指令丢失。
满足时，推进器按测试 PWM 持续运转，直到有人手动恢复。

测试侧：`ThrusterMappingIntegrationTest::_missingNeutralAckKeepsQmlRecoveryJournal` 断言总共只发出 2 条 `DO_SET_SERVO`，
把"回中只发一次"固化成了预期；"正在输出时心跳中断"没有用例。

修复方向：仅对仍能确认是同一载具、同一输出的会话尽力重发回中，保留恢复记录；不要自动写回功能参数。
复核：成立；原定 S1，按本文自己的 S0 定义应为条件性 S0。

**T02 整个直测没有飞控侧的超时。**
`ThrusterDirectControlController.cc:443-450` 只有地面站一侧的时长定时器，`:474` 发出的指令不带时长。
QGC 崩溃、被关闭或电脑休眠时，结果同 T01，而且 QGC 自己无法补救。持续重发回中只能改善 QGC 还活着的情况，不能替代这一条的修复。

修复方向：采用经过验证的飞控侧限时方案。`MAV_CMD_DO_REPEAT_SERVO` 只是待评估选项：它回到的是 trim，未必是该推进器的中位；它与其他事件共用槽位，可能互相覆盖。
复核：成立；原定 S2 明显偏低，不能因为界面已告知就降级。

### S1

**N01 开启"禁用安全限制"后，手柄轮询线程和界面线程无保护地访问同一个按键动作对象。（Codex 发现，我已核对）**
轮询线程在 `Joystick.cc:818-823` 取出按键动作的裸指针并读它的名称、重复标志和计时器；
界面线程在 `Joystick.cc:1560-1562` 可以删除同一个对象，在 `:1570-1576` 可以改它的字段。两边之间没有锁，也没有快照。
官方代码里配置页和真实控制是二选一（`else if`），不会并行；我们的补丁（`Joystick.cc:799-800`）让配置期间也进入真实控制，竞态因此可达。
新增的原子标志只保护"是否允许控制"，保护不到对象本身。
触发条件：手柄已校准并启用、开关已开、停在配置页，同时反复改动作、选 `No Action` 或改重复。不需要真的按下按键。
后果：释放后访问，可能崩溃或执行错误的动作。
修复方向：在小临界区内复制所需的值再到锁外执行，或编辑期间受控地暂停轮询。

**N02 视频接收器销毁时不等工作线程真正结束。（Codex 发现，我已核对；官方 v5.1.5 原样如此）**
`GstVideoReceiver.cc:91-94` 析构时先排入停止任务再让工作线程退出；`:1790-1794` 只等 2 秒且不看结果。
而停止流程里录像收尾可等 3 秒（`:339-381`），另有一处无限等待（`:395-396`）。超过 2 秒时，线程还在跑，它的所有者已经析构。
后果：Qt 致命错误，或任务继续使用已失效的对象。正常关闭不一定触发，取决于收尾耗时。
修复方向：停止与等待使用同一个完成约定，没停完不销毁；单纯把 2 秒加大覆盖不了无限等待。

### S2

**F01 视频自动重连有次数上限，用尽后不再自动恢复。**
`VideoTile.qml:42` 的 `maxAutoRetries: 6`，退避 2.5、5、10、20、30、30 秒（`:220-240`）。
在一直没有新画面、也没有人手动操作的情况下，约两分钟后该路进入"连接失败"，必须手动点"重连"。
代码里已有 `maxAutoRetries <= 0` 表示不限次数的语义（`:205-206`），改成封顶退避即可。需要你确认上限是不是有意设计。
复核：部分成立。计数清零不只发生在出图时，手动重连、改配置也会清零；"两分半"是粗估，不是精确时限。

**F02 帧计数取自解码输出，不代表画面实际显示。**
`DeepSharkVideoController.cc:573-578`、`:603-604` 的探针挂在 sink 的输入端。画面年龄 watchdog（`VideoTile.qml:173`）和断联预警
（`DeepSharkConnectionMonitor.cc:269`）都用这个计数。解码正常但后面环节出问题时，画面冻住而指标正常。
复核：部分成立。sink 的 `frames-delivered` 也只表示调用了 `setVideoFrame`，不是屏幕呈现；映射失败另有报错通路，不是所有情况都会"假正常"。
修复时应把输入和交付两个指标分开用，并排除窗口最小化时有意停止交付的情况。

**F03 断联预警要等"飞控 + 全部已启用视频"都就绪才开始工作。**
`DeepSharkConnectionMonitor.cc:279`、`:288-313`。有一路已启用的相机从没出过图，监测就不武装，此后飞控心跳丢失也不触发这个预警。
复核补充：**所有视频都关闭时，飞控预警同样不会武装**（要求 `expectedCount > 0`）。
这个行为有测试固化，是现有设计；测试固化不等于需求合理。是否让飞控与视频分别武装，请你决定。

**F04 按键分配页：在"地面站动作"列重选 `No Action` 会把该按键的固件功能和 Shift 功能清零。**
`JoystickComponentButtons.qml:108-114`。只要选中的动作存在，就无条件把两个参数写成 0。
复核查了 Qt 6.11 源码：点击当前已选项也会触发 `activated`，所以"重选同一项"确实走这条路径。原值非 0 时就是一次对飞控的参数写入。
选一个真实的地面站动作时清零是有意的互斥（有测试断言）；`No Action` 不应清除。
复核：成立，不需要再靠运行来确认。

**F05 开启"禁用安全限制"后，手柄配置页里的按键和摇杆会真实控制机器人。**
`JoystickConfigController.cc:67-71`、`Joystick.cc:799-811`、`:985-997`。这是已授权的设计。
问题在提示：页面写的是"按下按键检查响应""按下按键高亮所在行"，没有告诉用户控制仍在实时发送。
复核：成立；与之相关的并发问题见 N01。

**F07 机器人已解锁时新连接上来，工具栏的解锁/上锁按钮不可用。**
`FlyViewToolBar.qml:112-117` 要求参数已就绪。已解锁的非 PX4 载具首次接入时跳过参数下载（`InitialConnectStateMachine.cc:91-105`），
跳过只设"已跳过"标志，不设"已就绪"（`ParameterManager.cc:1554-1559`），所以按钮是灰的。开启"禁用安全限制"时会补下载，不受影响。
典型场景：QGC 崩溃重启，机器人仍在水里解锁。
复核：成立，读码可确认。手柄和引导动作里仍有上锁路径，工具栏按钮不是全应用唯一入口；同一载具暂时丢通信不属于这个场景。

**F08 模式播报在 GUI 线程同步执行。** 见上一节。机制成立，是否为卡顿原因待测。

**F12 云台旧参数页的副作用写入。**
`APMGimbalInstance.qml:224-242`。任何一个旧版 `MNT_RC_IN_*` 的值变化都会把 `MNT_DEFLT_MODE` 写成 3，
包括参数页修改和飞控回读引起的变化。条件是旧参数存在且这个页面已打开。
复核：成立，原定 S3 偏低，可能无意中改变云台的默认模式。

**F20 诊断信息和日志带出 RTSP 地址里的用户名密码。**
