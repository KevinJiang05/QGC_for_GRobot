# QGC GRobot 性能基线与优化方向

## 实测摘要

- 日期：2026-09-08
- 构建：`build-debug-ai\Debug\QGC_KevinJiang.exe`
- 启动方式：`StartDeepSharkQGC.cmd`
- 视频：三路 1920x1080 RTSP，第四路停用
- AI：本轮基线中未运行
- 冷启动到进程出现：约 0.61 秒
- 冷启动到三路 RTSP TCP 会话建立：约 10.87 秒
- 稳定运行工作集：约 1.13-1.17 GB
- 私有内存：约 0.96-1.02 GB
- 线程：约 98-101，运行约一小时后为 91
- 句柄：约 3,877-4,067，运行约一小时后为 3,834
- GPU 本地显存：约 753-754 MB
- CPU：约 60%-70% 单核等效负载

连续约 60 秒采样中，工作集、私有内存、线程和句柄没有持续增长。运行约一小时后的内存、线程和句柄也没有显示出持续增长证据。

## 结论

当前没有短时间资源泄漏证据；CPU、GPU 和三路视频首帧等待仍有优化空间。Debug 构建不能代表最终 Release 安装包。

进程启动本身很快，用户感知的主要等待来自三路视频连接、媒体协商、解码和首帧建立。

## 已验证

- 三路 RTSP 会话可以同时建立。
- 全部重连后的动态视频 pad 连接问题已修复并现场验证。
- 当前短时间资源曲线稳定。
- GStreamer 视频日志可以通过 `--logging:VideoAllLog` 开启。

## 尚未完成的验证

- 连续 10 次全部重连后的资源曲线。
- 单路摄像头断流、断电、恢复后的资源和首帧时间。
- 运行 30 分钟以上的完整资源曲线。
- 关闭 AI overlay、最小化视频面板、停用第四路的 CPU/GPU 对照。
- Debug 与完整依赖 Release 包对照。
- 发布包 GStreamer DLL、插件和插件 scanner 的完整性。

## 当前日志能力

GStreamer 视频日志已覆盖：

- receiver 启动、停止和超时；
- streaming 和 decoding 状态；
- 非视频动态 pad 被忽略；
- decoder pad 处理；
- 视频 sink 连接成功或失败及 link 返回码；
- 三路 URI 级别的事件时间。

后续可以低频增加首帧耗时、帧率摘要、重连序号和 QML/receiver 状态对应关系，但应避免高频日志增加 CPU 或磁盘写入。

## 优化方向

### P1：先测量再改

1. 记录三路首帧时间，而不只记录 RTSP 建立时间。
2. 连续重连 10 次，比较内存、线程、句柄和 GPU 显存的首尾差异。
3. 分别测量关闭 AI overlay、最小化视频面板、停用第四路。
4. 用完整 Release 运行时重复冷启动和资源测量。

### P2：预计收益较高

1. 减少 `FourVideoPanel.qml` 每秒完整刷新，优先使用状态事件更新。
2. 停用视频通道时确认 receiver、sink、worker 和 GStreamer pipeline 都释放。
3. 将非首屏 3D、AI overlay 和任务面板保持为按需加载。
4. 对三路视频启动做可控错峰，改善首屏响应和瞬时资源压力。

### P3：发布与运维

1. 普通启动关闭详细视频日志，保留独立诊断启动模式。
2. 发布构建自动验证 GStreamer DLL、插件和 scanner。
3. 日志保留版本、构建类型、视频后端和关键配置摘要，但不记录密码、令牌或完整敏感 URL。

## 验收边界

完成 Release 对照、连续重连、断流恢复和长时间运行测试前，不作发布级性能结论。当前结果足以说明优化方向，但不足以证明所有硬件环境下均无资源问题。
