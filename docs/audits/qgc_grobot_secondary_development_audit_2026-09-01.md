## 1. 总体结论

这不是一个简单换 Logo、改颜色的 QGC 分支，而是已经形成了较完整产品方向的深度二次开发：四路视频、AI 检测叠加、AUV 工作区、3D 姿态、推进器/舵机诊断、ArduSub 固件元数据、默认通信链路、品牌化安装包和 Windows 发布审计链都已经落地。以个人或小团队二开项目衡量，产品想法、落地速度和场景理解明显高于普通 QGC 定制项目。

但当前工程成熟度仍更接近“功能丰富的工程样机/现场工具”，尚未达到“可长期维护、可重复验证、故障边界清晰的正式产品”。下列清单是首次审计时的判断；运行时 P0、AI UDP、默认 TCP 和地图 binding 已按第 0 节整改，未标记关闭的部分仍然成立：

1. 首次审计时，AI 为每路视频分别加载模型且 `maxFps` 不限制推理；本轮已改为单模型和推理前限帧，仍保留“显示与推理各解码一次”的待实测成本。
2. 首次审计时，视频重连存在 QML/C++ 双延迟所有者和不可取消任务；本轮已消除晚到启动，并限制重试次数。
3. 首次审计时推进器直接控制的状态、确认与 4 个执行 Timer 全在约 1710 行 QML 中；本轮已把直接输出/恢复状态机抽到 C++ 并补测试，QML 降至约 1583 行、47 个函数和 4 个非直接输出 Timer。Fact/Vehicle 适配和 recovery journal 仍保留在界面层，需真机验证后再决定是否继续拆分。

## 4. 最高优先级问题

## P0-1：AI 四路模式存在重复解码和多模型实例放大

> 整改状态：**主要结构已修复**。`run_yolo_to_qgc_auto.py` 现在单进程只加载一次模型，并批量处理各路到期最新帧；`collect_due_frames` 在 `model.predict` 前执行 `maxFps` 调度。仍需真实四路性能基准确认收益，且显示/推理双解码尚未合并。

### 首次审计证据（整改前）

- `custom/src/DeepShark/FourVideoPanel.qml:675-747` 创建最多四个 `VideoTile`，QGC/GStreamer 各自接收并解码视频。
- `tools/ai_detection/run_yolo_to_qgc_auto.py:94-124` 按视频源启动一个子进程。
- 每个子进程在 `tools/ai_detection/yolo_to_qgc_udp.py:117` 独立执行 `YOLO(args.model)`，随后为自己的源启动推理流（约 `124-135` 行）。

四路 AI 开启后，结构上相当于：

- QGC：4 路解码用于显示；
- Python：再做 4 路解码用于推理；
- 模型：最多 4 份实例/权重上下文；
- 进程：1 个启动器 + 4 个推理子进程。

这会放大 GPU 显存、系统内存、视频解码器、上下文切换和网络拉流压力。在嵌入式 GPU 或低功耗工控机上，它很可能成为整机性能瓶颈。

### 另一个语义问题

`yolo_to_qgc_udp.py:137-145` 的帧率间隔判断发生在 `for result in results` 已经产出推理结果之后。因此 `maxFps` 当前主要限制 UDP 消息发送频率，**不等于限制模型推理频率**。界面或文档若把它解释为性能档位，会误导用户。

### 首次审计建议（本轮已执行主要部分）

1. 先做 1/2/4 路基准：记录 QGC CPU、Python CPU、GPU 利用率、显存、系统内存、解码会话数、端到端延迟和掉帧。
2. 把 AI 改为一个长期存活的服务/父进程，只加载一份模型；多路源通过同一 worker 或有上限的 worker pool 调度。
3. 在进入推理前采样/丢帧，或者使用容量为 1 的“只保留最新帧”队列；不要在推理完成后才丢结果。
4. 长期可评估让显示与推理共享解码后的帧，但这属于较大改造；短期先消除 4 份模型实例收益最大。

验收标准：四路开启时模型仅加载一次；`maxFps=5` 时实测推理吞吐接近 5 FPS/路而非源帧率；停止 AI 后 GPU/子进程资源全部释放。

## P0-2：AI 子进程没有可靠地绑定到 QGC 生命周期

> 整改状态：**已修复原问题的正式路径**。自动桥接器不再创建每路子进程，QGC 只管理一个 Python 服务；本机 TCP 实例锁拒绝重复实例；`AIDetectionManager` 正常启停不再用同步等待阻塞 UI，并保留 3 秒强杀兜底。

### 已证实

- `src/FlightDisplay/AIDetectionManager.cc:209-243` 只持有并停止外层 `run_yolo_to_qgc_auto.py` 的 `QProcess`。
- Python 启动器用 `subprocess.Popen` 创建多个子进程，但只在捕获 `KeyboardInterrupt` 时清理它们（`run_yolo_to_qgc_auto.py:137-145`）。
- QGC 对父进程执行 `terminate()`/`kill()` 并不保证 Python 进入 `KeyboardInterrupt` 分支。
- 根目录 `StartYoloToQGC.cmd` 还能在 QGC 外单独启动同一套 AI；应用内管理器无法识别这个外部实例。
- `StopDeepSharkQGC.cmd` 的模式主要针对旧的外部 DeepSharkViewStudio 流程，没有可靠覆盖这些 YOLO 子进程。

结果是：关闭 AI、关闭 QGC、父进程异常或同时使用 CMD 与应用内启动时，可能出现孤儿进程、重复拉流、重复 UDP 和多倍 GPU 占用。

### 建议

- 只保留一个权威启动入口；推荐由 QGC 管理单一 AI 服务，CMD 仅作为明确标注的开发调试入口。
- Windows 下使用 Job Object，或至少使用可终止的进程组，并让父进程在正常信号、父管道断开和异常退出时统一清理全部子进程。
- 增加实例锁或控制端口握手，第二个启动请求应复用/拒绝，而不是再开一套。
- 停止流程必须等待服务确认、清空叠加结果，然后再进入强制终止兜底。

## P0-3：视频自动启动/重连存在双重所有者和不可取消延迟任务

> 整改状态：**已修复并增加回归测试**。不可取消的 `QTimer::singleShot` 和 QML `restartTimer` 已移除；延迟启动由 C++ 成员 Timer 持有，停止/清 URL/关闭自动启动都会取消；重连改为 C++ `restart()` 加 QML 有限指数退避。

### 已证实

`custom/src/DeepShark/VideoTile.qml` 同时使用启动、watchdog、重连延迟等 QML Timer；`custom/src/DeepSharkVideoController.cc` 又使用 `QTimer::singleShot` 延迟拉流。当前 C++ `stop()` 仅在 receiver 已处于 `started()` 时调用停止，而待执行的 single-shot 没有句柄和代次标识。

可以形成如下竞态：

1. `autoStart=true` 安排一次延迟启动；
2. 用户很快关闭或切换该视频；
3. 此时 receiver 尚未 `started()`，`stop()` 没有实际取消动作；
4. 旧 single-shot 到点后仍执行 `start()`，视频在用户停止后又被拉起。

同时，QML 的 `maxAutoRetries: 0` 表示无限重试，重试间隔基本固定在 3/5 秒。四个不存在的源会长期制造启动、超时和日志活动。

### 建议

- 把连接生命周期收口到 C++ 的单一状态机：`Stopped / Starting / Streaming / Backoff / Failed`。
- 使用可取消的成员 `QTimer` 和 generation token；任何 URL、可见性、autoStart 或用户停止变化都使旧 generation 失效。
- QML 只展示状态和发出意图，不再自行拥有一套并行重连状态机。
- 采用有上限的指数退避和 jitter；达到阈值后进入明确的“已暂停，点击重试”。
- 修正 sink 重建路径，避免 `setVideoItem -> rebuild -> ensureReceiver -> rebuild` 造成首次创建时的重复销毁/创建。

验收标准：快速开关、切 URL、切布局、窗口隐藏和网络断开恢复都有确定状态；停止后不存在晚到启动；无源时重试频率逐步下降。

## 11. 最终判断

项目的优势仍是“真正懂使用场景，而且能把想法做出来”；此前最突出的 AI/视频运行时所有权问题已经从原型式多进程、多 Timer 收口为可测试的单 owner 路径，推进器直接输出/恢复也拥有了独立可测的 C++ 状态机，AI UDP、AUV Plan、默认 TCP 和地图 binding 的主要行为风险已关闭。标准发布验证已经固化为 RC/正式发布门禁，不再算当前 P1；现阶段短板主要是真实负载与真机安全证据不足，以及仓库制品治理尚未关闭。

本轮已经完成的三项是：

1. AI 收成单模型、单 owner、推理前限帧且拒绝重复实例的服务；
2. 视频延迟启动改为可取消的单 owner，并把无限固定重连改为有限指数退避；
3. 为上述路径补最小 Python/Qt Test 和真实自定义 CI 触发面。

本轮追加完成的三项是：

1. AI UDP 收口到 loopback，并增加输入上限、时间戳校验、结果过期和清空测试；
2. 默认 TCP 只在不存在时创建，不再覆盖用户已经保存的端点或自动连接选择；
3. 地图可见/交互状态恢复由 `FlyView` 单一持有，消除自定义层破坏 binding 的路径。

本轮随后完成 P1-2：推进器直接输出与恢复流程迁入可测试的 C++ 状态机，QML 保留飞控适配、恢复 journal 和界面文案，4 个直接控制 Timer 已从 QML 删除。
