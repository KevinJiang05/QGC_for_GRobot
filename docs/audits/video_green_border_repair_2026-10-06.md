# 新版视频绿边修复复核

日期：2026-10-06。范围：v5.1.5 Debug 的 Windows D3D11 视频显示路径。

## 原因与修复

- 现场摄像头有效画面及 GstVideoMeta 均为 1920×1080，NV12 D3D11 原生纹理为 1920×1152；底部 72 行是解码器分配的填充区域。
- 原代码按有效画面尺寸导入整张原生纹理，Qt 的归一化采样仍覆盖了填充区域，导致视频底部绿边。
- `GstD3D11VideoBuffer::resolvePlaneResources()` 现在核对原生纹理与有效画面尺寸。存在填充时，在 GPU 上只复制有效区域；原有数组切片复制也使用有效区域尺寸。
- 首次修复启用了原有的全局三槽纹理池，用户确认绿边消失，但三路视频发生抽搐、串画面。该池只按尺寸和格式区分纹理，会在仍有帧持有旧纹理时轮转覆盖它，无法保证多路视频的帧内容隔离。
- 最终移除 D3D11 全局暂存纹理池。每帧的暂存纹理由该帧及 Qt 纹理对象持有，在这些持有者释放后销毁，后续帧不会覆盖仍在显示的纹理。普通无需复制的纹理仍使用原有导入与纹理对象复用路径。
- 普通无填充、无数组切片的纹理仍直接导入。生产路径不增加 CPU 图像回读，不修改摄像头、飞控参数或 QML 画面缩放。
- 已有 viewport 裁切信息保持原值。原生纹理小于声明的有效画面时，沿用现有构造失败及 CPU 回退路径。

仅给大纹理设置 viewport 的方案未采用：本机 Qt 6.11.1 实测 640×368 分配、640×360 viewport 时，VideoOutput 仍以 640×368 计算显示比例，导致 640×360 容器内画面宽度变为 626.09。这与 [Qt 6.11.1 VideoOutput 源码](https://raw.githubusercontent.com/qt/qtmultimedia/v6.11.1/src/multimediaquick/qquickvideooutput.cpp) 中向 `_q_newFrame` 传递 `frame.size()` 的行为一致。最终 GPU 复制方案保持声明尺寸和实际纹理尺寸一致。

## 验证

- 增量 Debug 构建成功。最终 SHA256：`A474BDC78316D82C69C8CAC07F6AD5E66F7B475B4C640736242E85D4909BE9A8`。
- 只运行 `GStreamerTest`，未重跑全量 Unit：107 项，97 通过，10 项因平台或依赖不支持跳过，0 失败，Qt 测试耗时 3.635 秒。
- 新增五个回归场景全部执行并通过：无填充、底部填充、右侧与底部填充、已有显式裁切、真实 H.264 硬件解码产生的数组纹理填充。
- 回归检查原生 ID3D11Texture2D 的实际尺寸及 ArraySize，并将源纹理和输出纹理回读比较：有效区域的 NV12 亮度、色度逐行相等。回读仅发生在测试中。
- 在需要复制的各场景中，同时保留五帧的原生纹理，验证后续帧的纹理地址不会与任何仍存活的先前帧重复；全部通过。
- 变更文件的八项适用 pre-commit 检查、clang-format 变更行检查、`git diff --check` 通过。
- 首次重启后的实际 GPU 导入日志为 `size= QSize(1920, 1080) format= 18 planes= 2`，用户随后确认绿边消失并报告串画面；该次试跑未通过视觉验收。
- 帧所有权修复后已再次重启新版，最终进程 PID 61244、窗口响应正常，三路 RTSP 和飞控 TCP 连接恢复，实际 GPU 导入尺寸仍为 1920×1080。
- 用户最终确认：“现在画面稳定正常”。本次实际试跑通过绿边和多路串画面视觉检查。

每帧独立暂存纹理会增加 D3D11 纹理创建次数；本轮优先消除已复现的内容覆盖。测试结果不代表三路实机视频长期性能验收。

## 手柄链路检查边界

按用户最新要求，`Lost manual control` 暂不扩展修复。已检查本地手柄校准和启用状态、25 Hz 轴频率设置，以及 Joystick → Vehicle::sendJoystickDataThreadSafe → MANUAL_CONTROL → primaryLink 的发送调用链；未发现这些基础配置或打包调用的明显缺口。未实测持续发送频率或飞控接收间隔，不能据此排除偶发中断。

本轮没有修改旧版 5.0.8，没有生成或分发安装包，没有发送电机控制指令或修改飞控失控保护参数。
